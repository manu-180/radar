# 18 — Scheduling autónomo con Supabase Cron

## Contexto
**Lead Detector** monitorea plataformas online buscando gente que busca contratar un developer, filtra los posts con IA (Claude) y avisa por WhatsApp. Stack: Next.js (App Router) + Supabase + Claude API + Wassenger + Vercel.

Paso **18 de 35**.

**Ya existe:** las rutas `/api/cron/dispatch`, `/api/process` y `/api/notify`, protegidas con `x-cron-secret` (12, 15, 17); esquema Supabase aplicado (03). MCP de Supabase conectado.

Este paso hace que el sistema corra **solo, sin intervención humana**.

## Por qué Supabase Cron (y no Vercel Cron)
El cron del plan **Hobby de Vercel** solo permite frecuencia **diaria** — inservible para polling cada 20 min. **Supabase Cron** (`pg_cron`) corre dentro de Postgres, soporta frecuencia sub-minuto y dispara HTTP con `pg_net`. Gratis.

## Tarea
1. **Habilitar extensiones** — con el MCP, verificar con `list_extensions` y habilitar: `create extension if not exists pg_cron;` y `create extension if not exists pg_net;`
2. **Guardar el secreto** — guardar `CRON_SECRET` en **Supabase Vault** (`vault.create_secret`) con el nombre `cron_secret`. (Si Vault no estuviera disponible, es aceptable inlinearlo: la base es privada y cerrada por RLS.)
3. **Crear `supabase/cron.sql`** — script **idempotente**: para cada job, `cron.unschedule` si existe y después `cron.schedule` con un `net.http_post` a la ruta, con los headers `Content-Type: application/json` y `x-cron-secret`. URL base = `APP_URL`. Jobs:
   | Nombre | Cron | Ruta |
   |---|---|---|
   | `lead-detector-poll` | `*/20 * * * *` | `/api/cron/dispatch` |
   | `lead-detector-process` | `5-59/20 * * * *` | `/api/process` |
   | `lead-detector-notify` | `12-59/20 * * * *` | `/api/notify` |
   (El job de health se agrega en el paso 26.)
4. **Aplicar** el script con el MCP (`execute_sql`).
5. **Documentar en el README** que los jobs apuntan a `APP_URL`; en el paso 33 (deploy) se re-corre `cron.sql` con la URL de producción.

## Decisiones de diseño
- Etapas desacopladas: si una falla, las otras siguen; cada una es idempotente.
- El script es idempotente (`unschedule` + `schedule`): se re-corre sin duplicar jobs.

## Criterio de éxito
- `list_extensions` muestra `pg_cron` y `pg_net` habilitadas.
- `select jobname, schedule from cron.job` muestra los 3 jobs.
- `supabase/cron.sql` existe, es idempotente y está aplicado.
