# 02 — Infraestructura compartida: HTTP, logging y seguridad

## Contexto
**Lead Detector** monitorea plataformas online buscando gente que busca contratar un developer, filtra los posts con IA (Claude) y avisa por WhatsApp. Stack: Next.js (App Router) + Supabase + Claude API + Wassenger.

Paso **02 de 35**.

**Ya existe:** proyecto Next.js, `lib/env.ts`, `lib/supabase/admin.ts`, Vitest configurado (pasos 00–01).

Este paso construye los **módulos compartidos** que usa todo el sistema. Centralizarlos acá evita que cada adaptador y cada ruta reimplemente fetch, timeouts y logging de forma inconsistente — es la base de robustez del proyecto.

## Tarea
1. **`lib/http.ts`** — `fetchWithRetry(url, options)`:
   - Timeout por request con `AbortController` (default 15 s).
   - Reintentos (default 3) con **backoff exponencial + jitter** ante errores de red y ante status `429`, `500`, `502`, `503`, `504`, `529`.
   - Respeta el header `Retry-After` si viene.
   - `User-Agent` configurable por opción.
   - Devuelve la `Response` si es 2xx; tras agotar los reintentos, lanza un error descriptivo (incluyendo URL y último status).
2. **`lib/logger.ts`** — `createLogger(context?)`:
   - Devuelve `{ info, warn, error }`; cada uno emite **una línea JSON** con `ts`, `level`, `msg` y los campos de `context` + los del llamado.
   - Método `child(extra)` para enlazar contexto adicional (ej. un `runId`).
   - Sin dependencias externas: un wrapper fino sobre `console`.
3. **`lib/security.ts`**:
   - `timingSafeEqualStr(a, b): boolean` — comparación de tiempo constante con `crypto.timingSafeEqual` (manejá longitudes distintas sin filtrar timing).
   - `verifyCronSecret(request): boolean` — lee el header `x-cron-secret` y lo compara timing-safe con `env.CRON_SECRET`.
4. **Tests** en `test/`: un test de `timingSafeEqualStr` y, mockeando `fetch`, un test de que `fetchWithRetry` reintenta ante un `503` y luego resuelve.

## Decisiones de diseño (respetalas)
- **Todos los adaptadores y rutas** usan estos módulos en vez de reimplementar fetch/timeout/logging.
- No agregar librerías para esto: los tres módulos son chicos y sin dependencias.
- Los logs estructurados (JSON) permiten rastrear problemas en los logs de Vercel filtrando por `runId`.

## Criterio de éxito
- `npm test` pasa, incluyendo los tests nuevos.
- `fetchWithRetry` reintenta ante `503` y corta por timeout (verificado en el test).
- `npm run build` pasa.
