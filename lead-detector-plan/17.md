# 17 — Rutas de notificación por WhatsApp

## Contexto
**Lead Detector** monitorea plataformas online buscando gente que busca contratar un developer, filtra los posts con IA (Claude) y avisa por WhatsApp. Stack: Next.js (App Router) + Supabase + Claude API + Wassenger.

Paso **17 de 35**.

**Ya existe:** `lib/notify/wassenger.ts` (`sendWhatsApp`) y `lib/notify/message.ts` (`buildLeadMessage`) (16); esquema con `leads` (`notify_status`, `notified_at`), `notifications` y `settings` (`notify_rule`, `max_notifications_per_run`) (03); `lib/db/runs.ts` (11); `lib/security.ts`, `lib/logger.ts` (02); `WASSENGER_WEBHOOK_SECRET` en env (01). MCP de Supabase conectado.

Este paso **avisa al dueño por WhatsApp** cada lead calificado, una sola vez, sin condiciones de carrera.

## Tarea
1. **Migración `supabase/migrations/0003_claim_notify.sql`** — aplicarla con el MCP y regenerar `types/database.ts`:
   ```sql
   create or replace function claim_leads_to_notify(batch_size int, cats text[], min_score int)
   returns setof leads language sql as $$
     update leads set notify_status = 'sending'
     where id in (
       select id from leads
       where llm_status = 'done' and notify_status = 'pending'
         and (category = any(cats) or score >= min_score)
       order by first_seen_at limit batch_size
       for update skip locked
     )
     returning *;
   $$;
   ```
2. **`app/api/notify/route.ts`** (método `POST`; `dynamic = 'force-dynamic'`, `maxDuration = 300`):
   - Validar con `verifyCronSecret` → `401` si falla.
   - `startRun('notify')`; logger con `runId`.
   - Leer `settings.notify_rule` y `settings.max_notifications_per_run`.
   - Reclamar leads con `claim_leads_to_notify(maxPerRun, categories, minScore)` — reclamo atómico (`SKIP LOCKED`).
   - Por cada lead: armar el mensaje con `buildLeadMessage`, enviarlo con `sendWhatsApp(env.OWNER_WHATSAPP, ...)`, insertar fila en `notifications` (`status='sent'`, `wassenger_id`), setear `notify_status='sent'` + `notified_at = now()`. Esperar **3–5 s entre envíos**.
   - Si un envío falla: `notify_status='failed'`, insertar `notifications` con `status='failed'` y el error.
   - `finishRun(...)` con el conteo y el status.
3. **`app/api/webhooks/wassenger/route.ts`** (método `POST`):
   - **Verificar autenticidad**: comparar (timing-safe) un secreto contra `env.WASSENGER_WEBHOOK_SECRET` (header o segmento del path). Si no coincide, `401`.
   - Actualizar `notifications.status` (`delivered`/`failed`) por `wassenger_id`. Responder `200` rápido.

## Decisiones de diseño (respetalas)
- **Sin doble envío**: el reclamo atómico vía RPC (`notify_status` `pending → sending`) evita que dos corridas solapadas manden el mismo lead.
- **Tope por corrida** (`max_notifications_per_run`): ante un pico (ej. la primera corrida), se notifican N como máximo; el resto sale en los ticks siguientes.
- El webhook **debe** estar autenticado: sin verificación, cualquiera podría falsear estados de entrega.

## Criterio de éxito
- `POST /api/notify` envía un WhatsApp real por cada lead calificado y lo deja `notify_status='sent'` con `notified_at`.
- Una segunda llamada no reenvía; dos llamadas solapadas no duplican.
- Con más leads calificados que `max_notifications_per_run`, solo se envían N.
- El webhook rechaza (`401`) un POST sin el secreto correcto.
- Sin `x-cron-secret`, `/api/notify` responde `401`. `npm run build` pasa.
