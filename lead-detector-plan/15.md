# 15 — Migración de claim y ruta de proceso

## Contexto
**Lead Detector** monitorea plataformas online buscando gente que busca contratar un developer, filtra los posts con IA (Claude) y avisa por WhatsApp. Stack: Next.js (App Router) + Supabase + Claude API + Wassenger.

Paso **15 de 35**.

**Ya existe:** esquema con `leads` (columnas `llm_*`, `input_tokens`, `output_tokens`, `llm_cost_usd`, `score`, `category`, etc.) y `settings` (03); `lib/db/runs.ts` (11); `lib/ai/classifier.ts` con `classifyLead` (13); `lib/security.ts`, `lib/logger.ts` (02); `CRON_SECRET` y `APP_URL` en env (01). MCP de Supabase conectado.

Este paso construye la **ruta que clasifica los leads pendientes**, reclamándolos sin condiciones de carrera y drenando el backlog.

## Tarea
1. **Migración `supabase/migrations/0002_claim_leads.sql`** — aplicarla con el MCP y regenerar `types/database.ts`:
   ```sql
   create or replace function claim_pending_leads(batch_size int)
   returns setof leads language sql as $$
     update leads set llm_status = 'processing'
     where id in (
       select id from leads where llm_status = 'pending'
       order by first_seen_at limit batch_size
       for update skip locked
     )
     returning *;
   $$;
   ```
2. **`app/api/process/route.ts`** (método `POST`; `dynamic = 'force-dynamic'`, `maxDuration = 300`):
   - Validar con `verifyCronSecret` → `401` si falla.
   - `startRun('process')`; logger con `runId`.
   - Reclamar un lote con `claim_pending_leads(15)`.
   - Cargar una vez `settings.freelancer_profile` y los `feedbackExamples` (hasta `settings.feedback_examples_count` leads recientes con `feedback` seteado).
   - **Clasificar con concurrencia limitada**: procesar el lote en sub-lotes de ~5 con `Promise.all`.
   - Por cada lead: `classifyLead` con `claude-haiku-4-5`; si la categoría da `maybe`, reintentar con `claude-sonnet-4-6`.
   - **Éxito**: `update` con `score`, `category`, `reason`, `suggested_reply`, `llm_model`, `input_tokens`, `output_tokens`, `llm_cost_usd` (precios: Haiku 4.5 = in US$1 / out US$5 por millón; Sonnet 4.6 = US$3 / US$15), `llm_status='done'`. Si la categoría no califica según `notify_rule`, `notify_status='skipped'`.
   - **Error transitorio** (429/500/529/red de Claude): dejar el lead `pending` sin incrementar `llm_attempts`.
   - **Error real** (contenido/parseo): `llm_attempts + 1`; si `< 5`, volver a `pending`; si `>= 5`, `llm_status='failed'` con `llm_error`.
   - `finishRun(...)` con `itemsProcessed` y `status`.
   - **Drenado del backlog**: al terminar, contar leads `pending`. Si quedan y el header `x-drain-depth` (default 0) es `< 8`, disparar con `after()` un `fetch` a la propia `/api/process` con `x-drain-depth` incrementado.

## Decisiones de diseño (respetalas)
- `FOR UPDATE SKIP LOCKED` hace el reclamo seguro aunque dos corridas se solapen.
- **Errores transitorios vs. reales**: un 429/529 de Anthropic no quema intentos del lead.
- El **loop de feedback** calibra el clasificador con las decisiones reales del dueño (paso 21).
- El drenado con tope de profundidad vacía el backlog sin esperar al cron y sin bucle infinito.

## Criterio de éxito
- `POST /api/process` (con `x-cron-secret`) clasifica los leads `pending`: quedan `done` con `score`, `category`, `reason`, `suggested_reply` y `llm_cost_usd` no nulos.
- Un fallo transitorio simulado no incrementa `llm_attempts`.
- Con más de 15 leads pendientes, el drenado los procesa todos.
- Sin `x-cron-secret`, `401`. `npm run build` pasa.
