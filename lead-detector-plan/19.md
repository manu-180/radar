# 19 — Autenticación y layout del dashboard

## Contexto
**Lead Detector** monitorea plataformas online buscando gente que busca contratar un developer, filtra los posts con IA (Claude) y avisa por WhatsApp. Stack: Next.js (App Router) + Supabase + Claude API + Wassenger.

Paso **19 de 35**.

**Ya existe:** proyecto Next.js con Tailwind; `lib/env.ts` con `DASHBOARD_PASSWORD` y `AUTH_SECRET`; `lib/security.ts` con `timingSafeEqualStr` (00–02).

Este paso construye el **caparazón del dashboard**: login por password y layout con navegación. Es privado, de un solo usuario.

## Tarea
1. **`app/login/page.tsx`** — formulario con un campo de password.
2. **Server action de login**:
   - Comparar el password con `env.DASHBOARD_PASSWORD` usando `timingSafeEqualStr`.
   - Ante un intento fallido, aplicar una **demora deliberada** (~1 s) antes de responder.
   - Si coincide, setear una cookie `ld_session`: httpOnly, `secure` en producción, `sameSite=lax`, con expiración (~30 días). El valor es `<emitidoEn>.<HMAC>`, con el HMAC firmado con `env.AUTH_SECRET`.
3. **`middleware.ts`** — protege todas las rutas del dashboard: sin cookie `ld_session` con HMAC válido y no vencido, redirige a `/login`. Excluir `/login`, `/api/*` y assets estáticos.
4. **`app/(dashboard)/layout.tsx`** — layout con navegación a **Leads**, **Configuración** y **Métricas**, y un botón de **logout**.

## Decisiones de diseño
- Auth deliberadamente mínima (un password, cookie firmada con HMAC): panel personal, no multiusuario. No agregar Supabase Auth ni OAuth.
- La demora ante fallos + la comparación de tiempo constante mitigan el fuerza-bruta.
- El grupo `(dashboard)` no afecta la URL: las páginas resuelven a `/leads`, `/config`, `/metrics`.

## Criterio de éxito
- Entrar a una ruta del dashboard sin sesión redirige a `/login`.
- Con el password correcto se entra y la cookie persiste; con uno incorrecto la respuesta tarda ~1 s.
- Una cookie con HMAC manipulado es rechazada. El logout borra la cookie.
- `npm run build` pasa.
